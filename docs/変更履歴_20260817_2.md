# 変更履歴 2026-08-17 (第2弾)

## realtime版：初期読込が全件取得になっていた問題の修正

### 対象ファイル
- `html/ampere/realtime.html`

### 背景

同日のコミット `16e77a8`（[変更履歴_20260817.md](変更履歴_20260817.md)）で「JSONLのみ読む＋14日段階読込」を
入れた直後、**初期表示で依然としてほぼ全件が取得される**という指摘を受けた。
本番相当データ `C:\dev\amp-2\machine-tool-info-osaka`（1407ファイル / 3012MB /
2026-07-09〜2026-08-17）で実測したところ指摘は正しく、原因は3つあった。

### 前回記録の訂正

[変更履歴_20260817.md](変更履歴_20260817.md) は「CSVとJSONLの二重記録が主因」と結論づけているが、
これは**当時の検証サンプル `C:\dev\ampere-data` にしか存在しない過去の問題**だった。
現在の本番データに CSV は無く、真因は以下の①②である。前回の結論は現行データに対しては不正確。

### 真の原因（実測で確定）

#### ① 収集側のファイル名が 2026-07-27 19:00 に4フィールドへ変わっていた（決定的）

```
20260727_185959_xxx.jsonl        ← 3フィールド（〜07-27 18:59）
20260727_190000_079_001.jsonl    ← 4フィールド（07-27 19:00〜、480件）
```

`FILENAME_TS_RE` が3フィールドしか受け付けないため、**直近3週間分480件すべてで
`parseFileStartTime()` が `null`** を返し、`selectFilesInWindow()` の
「命名規則外は取りこぼさぬよう取り込む」フォールバックに落ちて無条件に取得されていた。
前回追加した mtime 安全弁も、これらは実際に新しいファイルなので素通りする。

| ウィンドウ | 修正前 | 修正後 |
|---|---|---|
| **1日** | **961 files / 2121 MB** | 25 files / 62 MB |
| 7日 | 973 files / 2152 MB | 175 files / 446 MB |

**1日ウィンドウでも 2121MB（全体の70%）取得していた。**

#### ② `_001` は同一ストリームの二重記録

`20260817_100000_433.jsonl` と `20260817_100000_433_001.jsonl` を比較すると、
時間範囲（10:00:00.433〜10:59:58.644）・行数（8079行）が完全一致、94.7%がバイト一致、
差分は `ingest_t` のミリ秒ジッタのみ。同じMQTTストリームを2プロセスが並行記録している。
3フィールド名だけで全期間をギャップなくカバーしており（3時間超の間隔は0箇所）、
`_001` 側は真部分集合。

#### ③ 段階読込のチェーンが即時で、絞る意味がなかった

`expandWindowIfNeeded()` を `finally` で呼んで**待ち時間ゼロで次の `poll()` を連鎖**させていたため、
全段が一気に走りきっていた。初回描画が速くなるだけで初期取得量は1バイトも減っていなかった。

### 変更内容

#### 1. ファイル名パーサを4フィールド対応にし、重複排除の材料を返す

```js
const FILENAME_TS_RE = /^(\d{4})(\d{2})(\d{2})_(\d{2})(\d{2})(\d{2})_(\d{3})((?:_\d+)*)\.jsonl$/i;

function parseFileName(name) {
  const m = FILENAME_TS_RE.exec(name);
  if (!m) return null;
  const [, y, mo, d, h, mi, s, ms, extra] = m;
  return {
    t: new Date(Number(y), Number(mo) - 1, Number(d), Number(h), Number(mi), Number(s), Number(ms)),
    base: `${y}${mo}${d}_${h}${mi}${s}_${ms}`,
    depth: extra ? extra.split('_').length - 1 : 0
  };
}
```

`parseFileStartTime()` は `parseFileName()` の薄いラッパーにしたので、
`selectFilesInWindow()` 側は無変更。mtime 安全弁もそのまま生きている。

#### 2. `dedupeByBase()` を追加し、`poll()` で dedupe → sort → select の順にする

同一 base 時刻のファイルが複数あれば、余分なフィールドが少ない方（＝plain）を1つだけ採用する。
plain が無い base では `_NNN` 付きが採用されるため、**将来 plain が廃止されてもデータが消えない**。
命名規則外のファイルはそのまま通し、既存の mtime フォールバックに判断を委ねる。

重複を除いてからソートするので、`selectFilesInWindow()` が守備範囲の終端に使う
「名前順で次のファイル」が本当に次の記録になる（混在時の誤判定も同時に解消）。

#### 3. 命名規則外ファイルの検知ログ

同じ罠を三度踏まないよう、`poll()` でパース不能ファイル数を数え、件数が変わったときだけ
`console.warn` を出す（`lastUnparsedCount` で抑制）。

#### 4. 初期読込の到達目標を 7日 に変更（14日から）

実測で 14日 = 808MB、7日 = 446MB。1日あたり約50MB。
7日より前は、ユーザーが範囲を変更したタイミングでのみ取得する。

#### 5. 段階読込を「ポーリング間隔ごとに1段」にする（今回の要点）

```js
} finally {
  polling = false;
  if (backfillPending) { backfillPending = false; poll(); }   // ユーザー起点の遡りは即時
  else {
    // 段階読込は下限を広げるだけにして、取得は次回のポーリングに任せる。
    // ここで即座に poll() を連鎖させると全段が一気に走りきり、初期取得量が絞れない。
    if (!failed) expandWindowIfNeeded();
    scheduleNext();
  }
}
```

#### 6. プリセットボタンから遡り取得を発火させる

従来は `start` を読込済み範囲にクランプするだけで `requestBackfill()` を呼んでいなかったため、
初期読込が7日だと「直近14日」を押しても何も起きなかった。クランプをやめて遡りを発火させる。
要求範囲にまだデータが無い間はグラフ左側が空くが、取得完了に従って埋まる。

### 触っていない箇所（意図的に維持）

- `setRange()` / `renderChart()` の relayout 競合対策、`userPinnedRange` の追随ロジック
- `selectFilesInWindow()` 本体と mtime 安全弁（`parseFileStartTime` 経由で自動的に直る）

- `classifyPayload()`
- `html/ampere/index.html`（D&D版）と `html/rs232/yao/realtime.html`

### 動作確認

検証データは `C:\dev\amp-2\machine-tool-info-osaka`（1407ファイル / 3012MB /
2026-07-09〜2026-08-17）。最新データが当日なので `Date.now()` の差し替えは不要。

#### 1. ロジックの単体確認（Node）

写経ミスを避けるため、**編集後の `realtime.html` から `parseFileName` / `dedupeByBase` /
`selectFilesInWindow` などを正規表現で抜き出して `new Function` で評価**し、実データに適用した。

- パース不能ファイル **0件**（修正前は480件）
- `dedupeByBase` で **1407 → 927 files / 3012 → 1953 MB**、`_001` 残存 0件
- 重複排除後の隣接ファイル間隔で **3時間超のギャップ 0箇所**（＝取りこぼしなし）
- ウィンドウ別：1日=25/62MB、2日=50/126MB、7日=175/446MB
- 段階読込シミュレーション：62 → 195 → 318 → 446 MB の4段で7日到達
- mtime 安全弁の回帰（命名規則外＋古いmtime=除外、新しいmtime=含む、mtime無し=含む）

#### 2. ブラウザでの実地確認

Docker daemon が起動していなかったため、nginx の `autoindex_format json` + Range 配信を模した
使い捨て Node サーバー（転送量カウンタ付き）をスクラッチパッドに用意して代替した。
`docker-compose.yml` は変更していない。

- **初期取得量**：1回目のポーリングで **25ファイル / 61.5MB** に収まることを確認
  （修正前は961ファイル / 2121MB）。
- **ペース制御**：2段目以降が即座に始まらず、10秒間隔で1段ずつ進むことを確認。
  7日到達後は自動拡張が止まり `接続OK` のままになる。
- **7日到達時の総量**：175ファイル / 446.4MB（Node予測と完全一致）。
- **`_001` 不取得**：サーバー側カウンタで `_NNN` 付きへのリクエストが全工程を通じて **0件**。
  ファイル一覧パネルにも出ない。
- **範囲追随**：段階読込に合わせて「開始」欄が過去へ伸び、完了時に `2026-08-10T11:00`
  （ちょうど7日前）になることを確認。
- **7日より前の取得**：「直近14日」ボタンで遡りが発火（範囲が 2026-08-03〜2026-08-17、
  ステータスが「過去データ読込中…」）、完了後 **347ファイル / 807.6MB**（Node予測と一致）、
  読込点数 2,036,012。
- **追随再開**：「全期間」で読込済み全期間（2026-08-03 11:00〜）に戻ることを確認。
- Console エラーなし。命名規則外が0件のため警告も出ない。

確認後、検証用サーバーは停止。スクラッチパッドの成果物はリポジトリに持ち込んでいない。
