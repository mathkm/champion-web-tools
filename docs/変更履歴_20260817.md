# 変更履歴 2026-08-17

## realtime版：初期読込を「直近14日・段階読込」に整理し、CSV/JSONL二重記録を解消

### 対象ファイル
- `html/ampere/realtime.html`

### 背景・目的

ユーザーから「過去の全件を取得している。初期表示は直近2週間に限定してほしい」という依頼を受けて
調査したところ、`INITIAL_WINDOW_DAYS = 7` と `selectFilesInWindow()`（[変更履歴_20260716.md](変更履歴_20260716.md)
で導入）自体は正しく動作していた。実際の原因は次の2点だった。

1. **CSV と JSONL の二重記録**：`/opt/machine-tool-info-osaka` では 2026-07-09 15:59 頃から
   収集フォーマットが CSV から JSONL へ移行したが、しばらくの間は同一データが両形式で書かれていた。
   `fetchListing()` は `/\.(csv|jsonl)$/i` で両方拾っていたため、点数・通信量が単純に2倍になっていた。
2. **単純な日数拡大は逆効果**：7日→14日にすると読込量がそのまま倍増する
   （サンプル `C:\dev\ampere-data` 実測で 382MB→962MB）。何もしなければ初期表示が大幅に遅くなる。

副次的に、`selectFilesInWindow()` は「名前順で次のファイル」を守備範囲の終端とみなすため、
csv/jsonl 混在下では境界誤判定が起きていたが、これは①の対応（jsonl のみ読む）で解消した。

### 変更内容

すべて `<script>` 内の IIFE への変更。

#### 1. jsonl のみを対象にする

`FILENAME_TS_RE` から `csv` を除外し、`fetchListing()` のフィルタも `/\.jsonl$/i` のみに変更。
CSV は完全に無視する（`classifyCsvText()` の CSV 分岐自体は D&D版 `index.html` と共通ロジックのため残置）。

```js
const FILENAME_TS_RE = /^(\d{4})(\d{2})(\d{2})_(\d{2})(\d{2})(\d{2})_(\d{3})\.jsonl$/i;
...
return arr.filter(e => e.type === 'file' && /\.jsonl$/i.test(e.name));
```

#### 2. 初期読込を「段階読込」に変更

最終的な読込範囲は14日前まで広げるが、起動直後にいきなり14日分をダウンロードすると
初期表示が遅くなるため、まず直近1日を読んで即描画し、以後ポーリングのたびに2日ずつ
過去へ広げていく方式にした。

```js
const INITIAL_WINDOW_DAYS = 14;   // 最終的に揃える遡り日数(段階読込の到達目標)
const FIRST_CHUNK_DAYS = 1;       // 起動時にまず読む日数(第1段。ここまで読めたら即描画)
const BACKFILL_STEP_DAYS = 2;     // 段階読込で1ポーリングごとに遡る日数
...
let targetWindowStartMs = Date.now() - INITIAL_WINDOW_DAYS * DAY_MS;  // 到達目標(=14日前)
let loadWindowStartMs   = Date.now() - FIRST_CHUNK_DAYS * DAY_MS;     // 現時点で読み込み済みの下限
```

`poll()` の `finally` で、通常のバックフィル要求（`requestBackfill`）が無ければ
`expandWindowIfNeeded()` を呼び、まだ目標に届いていなければ即座に次の `poll()` を連鎖させる。
通信エラー時は連鎖させない（タイトループ防止）。

```js
} finally {
  polling = false;
  if (backfillPending) { backfillPending = false; poll(); }
  else if (!failed && expandWindowIfNeeded()) { poll(); }  // 段階読込の次段へ
  else scheduleNext();
}
```

ユーザーが「開始」欄に14日より前の日時を入れて明示的に遡り取得を要求した場合は、
目標（`targetWindowStartMs`）も一緒に引き下げる（そうしないと `expandWindowIfNeeded()` が
「目標達成済み」と誤判定してしまうため）。

#### 3. 表示範囲を「読込済み全期間」に追随させる

段階読込では `series` が過去方向に伸びていくため、初期描画時に固定した表示範囲のままだと
グラフが1日分のまま広がらなくなる。「ユーザーが範囲を明示操作したか」を表すフラグ
`userPinnedRange` を導入し、未操作の間だけ読込済み全期間へ自動追随するようにした。

```js
let userPinnedRange = false;
...
function refreshView() {
  if (!userPinnedRange) {
    setRange(null, null, 'live');   // 読込済み全期間へ追随
  } else if (liveFollow) {
    setRange(fromLocalInputValue(rangeStartInput.value), null, 'live');
  } else {
    setRange(fromLocalInputValue(rangeStartInput.value), fromLocalInputValue(rangeEndInput.value), 'live');
  }
  renderChart();
}
```

フラグは、日時入力欄の変更・「全期間」以外のプリセット・グラフのドラッグズームで `true` に、
「全期間」プリセットとダブルクリックによる autorange リセットで `false` に戻す。

`setRange()`/`renderChart()` の relayout 競合対策（[変更履歴_20260716.md](変更履歴_20260716.md) で
修正済みの「ライブ追従で開始がリセットされる」バグの対処箇所）には一切手を入れていない。

#### 4. 命名規則外ファイルへの安全弁

ファイル名がパースできない場合に無条件で取り込んでいたフォールバックに、
nginx の autoindex JSON が返す `mtime` による足切りを追加した。最終更新がウィンドウより
古ければ確実に除外し、`mtime` が取れない場合のみ従来どおり取りこぼし防止で取り込む。

```js
function fileMtimeMs(entry) {
  if (!entry || !entry.mtime) return null;
  const t = Date.parse(entry.mtime);
  return Number.isNaN(t) ? null : t;
}
```

#### 5. プリセットボタンに「直近7日」「直近14日」を追加

`hoursMap` に `'7d': 168, '14d': 336` を追加し、既存の「`dataEnd - hours`、`dataStart` でクランプ」
ロジックをそのまま利用。

### 触っていない箇所（意図的に維持）

- 行単位の時刻フィルタは入れていない（[変更履歴_20260716.md](変更履歴_20260716.md) §3 の設計判断を継続）。
- `MAX_POINTS = 150000` は据え置き。14日分だと従来の7日時点の約2倍の点数を保持することになるが、
  今回のスコープ外。
- `poll()` の `series.ch0.sort()` 全体ソートは維持（段階読込で過去方向に点が追加されるため）。
- `html/ampere/index.html`（D&D版）と `html/rs232/yao/realtime.html` は変更していない。

### 動作確認

本番データ（`/opt/machine-tool-info-osaka`）は Linux ホスト側にあり手元から直接検証できないため、
以下の2段階で確認した。

#### 1. 選別ロジックの単体確認（Node）

本番相当のサンプル `C:\dev\ampere-data`（496ファイル、csv 160 / jsonl 336、2026-07-08〜07-24）の
ファイル名一覧に対し、実装後の `parseFileStartTime` / `selectFilesInWindow` をそのまま実行した。

- jsonl 336件全件が `parseFileStartTime` でパースでき、`null` は0件。
- 最終ファイル時刻を基準にウィンドウを 0/1/3/7/14/30日 と広げたとき、選択件数が
  1 → 25 → 74 → 170 → 317 → 336(全件) と単調に増加することを確認。
- 命名規則外のダミーファイルを混ぜたテストで、`mtime` が古い（ウィンドウより前）ものは除外され、
  `mtime` が新しいもの・`mtime` が無いものは取り込まれることを確認（安全弁が意図どおり動作）。
- `windowStartMs = 0` で jsonl 全件が選ばれることを確認。

#### 2. ブラウザでの実地確認

Docker daemon が起動していなかったため、`docker-compose.yml` の代わりに nginx の
`autoindex_format json` + Range 配信を模した使い捨ての Node 静的サーバーをスクラッチパッドに用意し、
`C:\dev\ampere-data` を配信して実機（Chromiumベースのブラウザペイン）で確認した。
サンプルデータの最終時刻（2026-07-24 15:00頃）が実行時の現在日時から3週間以上前だったため、
検証用にのみ `Date.now()` を `2026-07-24 18:00` 固定に差し替えたページコピーを使用した
（本体の `realtime.html` は変更していない）。ポーリング間隔も検証用コピーでのみ1.2秒に短縮した。

- **段階読込**：起動直後は直近1日分のみ読み込んで即描画され、以後
  `過去データ読込中… (あと約N日分)` を表示しながら2日刻みで過去へ広がり、最終的に
  ファイル数315（14日ウィンドウの選別結果と整合）で `接続OK` に到達することを確認。
- **CSV を読んでいない**：Network に `.csv` へのリクエストが1件も発生しないことを確認。
- **表示範囲の追随**：段階読込の進行に合わせてグラフ x 軸と「開始」欄が過去へ伸びることを確認。
  ただし実データには 2026-07-16 15:42 より前の JSONL に `sensor_type` を持たない別スキーマ
  （後述）が混在しており、そのファイルは取得はされるが有効点数0のため、表示範囲は
  「有効なデータが存在する範囲」（07-16 15:42〜07-24 15:40）に追随した。追随ロジック自体は
  意図どおり動作している。
- **追随の停止/再開**：「直近6時間」クリック後、複数回のポーリングを挟んでも範囲が
  勝手に広がらないこと、「全期間」クリックで追随が再開し読込済み全期間に戻ることを確認。
- **14日より前への遡り**：「開始」欄に2026-07-05を入力すると `requestBackfill` が発火し、
  目標が引き下げられてファイル数が315→336（jsonl全件）まで増加。「開始」欄の値も
  ポーリングを挟んでリセットされないことを確認（既知バグの再発なし）。
- **プリセット**：「直近7日」「直近14日」ボタンが動作することを確認。
- ブラウザ Console にエラーは出ていないことを確認。

確認後、検証用サーバーは停止済み。使い捨てサーバー・検証用HTMLコピー・Nodeスクリプトはいずれも
スクラッチパッド内のみで作業し、リポジトリには持ち込んでいない。

### 検証中に見つかった別問題（今回のスコープ外・対応していない）

サンプルデータの調査中、2026-07-16 15:42 より前の JSONL ファイルが、現行の2種類
（旧定義 `ch0_A`/`ch1_A`、新定義 `sensor_type`+`value`）のどちらとも異なる第3のペイロード形式
（`payload: {sensor_no, value, ip}` — `sensor_type` を持たない）で書かれていることが分かった。
`classifyPayload()` はこの形式を判定できずスキップするため、該当ファイルはネットワーク取得は
されるものの有効データ点数が0になる。`classifyPayload()` は本プランの対象外のため変更していない。
別途対応が必要であれば、この形式が本番データに現存するか（今回のサンプルが古い一時期のものか）を
確認したうえで検討する。

### 備考・既知の制約

- [変更履歴_20260716.md](変更履歴_20260716.md) に記載の制約（境界跨ぎファイルの誤差、行フィルタを
  入れない設計判断）はそのまま引き継いでいる。
